# TDD 与测试规范

## 原则

功能采用 RED → GREEN → REFACTOR：

1. 先从玩家、房主或攻击者的可见行为写失败测试。
2. 运行并确认失败原因是没有实现，而不是测试环境错误。
3. 写最小实现使场景通过。
4. 在测试保护下重构，保持严格类型检查。

测试不依据类名和私有方法堆砌，而依据业务场景命名。例如“全员提交后立即揭晓”“重复操作重发保持幂等”“服务重启后恢复票型”。

## 分层

- **business**：纯领域规则，快速覆盖所有阶段、平票、越权、非法输入和快照兼容。
- **network**：启动真实 Fastify 端口，通过 HTTP 和 `ws` 客户端验证鉴权、广播、私密视图、心跳、限流、多标签页、超时和重启。
- **ui**：React Testing Library 从角色、标签、按钮和可见文本验证用户行为；网络适配器可替换，但不 mock 被测组件。
- **e2e**：Playwright 启动生产服务，以三个隔离浏览器上下文完成三轮对局、手机刷新恢复和再来一局。

## 门禁

`pnpm check:all` 依次执行：

1. 业务/E2E 以及所有工作区的 TypeScript 检查。
2. 业务与网络测试及覆盖率阈值。
3. UI 行为测试。
4. 生产构建。
5. 真实浏览器 E2E。

覆盖率全局最低：语句 85%、函数 85%、分支 80%、行 85%。不得为了让 CI 变绿而降低阈值或删除有意义的断言。

## 新增测试的要求

- 一个场景只验证一个业务承诺，但允许包含完整用户流程。
- 网络测试不能使用 mock WebSocket 替代真实连接。
- 对私密信息不仅检查 UI，还检查实际网络载荷。
- 每个异步测试必须有超时和可靠清理，避免悬挂端口。
- 不依赖固定房间码、随机题目或真实等待 60 秒；通过注入时钟/随机数控制边界。
- 失败截图、trace 和覆盖率文件不提交 Git。
